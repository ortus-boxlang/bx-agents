## [Unreleased]

- **Security: a request can no longer make the server read an image file.** `images: [ { path } ]` in a turn request went to `MessageBuilder`, which embedded any png, jpg, gif or webp the server could read and answered `There is no image file [path]` for one it could not. `TurnRunner` now takes `images` only when it was built with `localImages`, which only the in-process terminal does (a caller's `source` comes from a request header, so it is no proof). Over HTTP, from a gateway or a routine the key is dropped and logged by name; pictures travel as `attachments` with base64 data.
- **Security: a caller can no longer run a tool without its approval, or pick the model.** `TurnRunner.prepareTurn` passed the caller's `options` and `params` to bx-ai whole. bx-ai reads `options._resumeContext` and, with it, runs the tool calls the request carries without reaching the approval middleware, so a caller with `chat` scope could run any approval-gated tool (for example `skill_save`, a shared and persistent prompt injection) with one POST to `/invoke`, `/stream`, `/batch` or `/events`. The same pass-through let `params.model`, `options.apiKey`, `options.returnFormat` and `options.providerOptions` override the `agentApi.profiles` list. A new `TurnOptions` builds both from an allowlist (`options.profile`; `params.temperature` and `params.max_tokens`, range checked), drops every `_` key and everything else without an error, and logs the dropped names. Nothing that this repo sends needed another key: the web page, `AgentApiClient`, the terminal and the routines send `options.profile` at most. Docs: "What a turn accepts" in the Agent API guide.
- **Breaking: a built app is `app/` and `public/`, like the ColdBox BoxLang template.** `bxAgents build` writes `.build/app` (the generated code), `.build/public` (the web root and the only folder a server serves), `.build/lib` (ColdBox and its modules), `.build/runtime` (the engine config, the `bxagents` module and the BoxLang home), `.build/boxlang_modules` and `.build/miniserver.json`. **Rebuild every existing app**: `serve` refuses a build made before this layout and says so. `.build/app` is no longer the web root, so anything that served it (a script, a Dockerfile of your own, a `.bxaignore` whose patterns were relative to `.build/app`, which are now relative to `.build`) has to follow. The template is carried in the module as a pinned snapshot (`templates/coldbox-boxlang`, version and commit in its `VERSION`, refreshed with `tools/refresh-coldbox-template.sh`) and the build never reads the network.
- **The exposure fix: nothing but `public/` is served.** The old layout served the whole app folder, so `/config/agent-settings.json`, `/project/Agent.yml`, `/agent/instructions.md` and a listing of `/config/` and `/skills/` answered 200 to anyone who could reach the port, token or not. All of them answer 404 now, and so does every other file outside `public/`. The server now runs only `index.bxm` (a `passPredicate` in `miniserver.json`): a `.bx` class under the app, or a ColdBox module, is no longer executed by address (it answered 200 with an empty body). An address nothing routes is a small JSON `404` and not ColdBox's 500 error page. Covered over HTTP by `ServedLayoutSpec`. `public/includes/` lists its file names (the server turns directory listing on in code and `miniserver.json` has no key for it); it holds only what the browser loads.
- **Only the `bxagents` module is loaded.** `serve` used to add the machine's own module directory to the served app, which loaded every module installed there. The module is now copied into `.build/runtime/modules/bxagents` (to a work folder, then renamed, and skipped while a stamp of its `box.json` and jars is unchanged), `runtime/` is the BoxLang home, and no module directory of the machine is named anywhere: the `test` verb's child loads the module alone through a link as well. A decoy module in `~/.boxlang/modules` does not load in the served app, and does load in a server without that home (spec).
- **`public/Application.bx` is derived from the template's and changed.** It ends as a thin class that extends the generated base `app/bxagents/Application.bx`, or is your own root `Application.bx` pointed at that base (`bxagents.Application` is still the name you write). The base carries what the template's file does (the `COLDBOX_*` settings, the bootstrap call, `loadColdbox()`, `onRequestStart()`) plus the app name, sessions, datasource, schedulers, the data home and the registrations; the template's `onApplicationEnd`, `onSessionStart`, `onSessionEnd` and `onMissingTemplate` are not carried. Settings and the hooks `before()`, `after()` and `beforeRequest()` (and the lifecycle methods themselves) are what you can customize. See [Application.bx](docs/conventions/application-bx.md).
- **Generated config that never applied, now applies.** The ColdBox config was written as `config/ColdBox.bx` (ColdBox loads `config/Coldbox.bx`, so on a case-sensitive file system it was never loaded) with `coldbox = {` and `moduleSettings = {` (an unscoped assignment is local to `configure()` in BoxLang). The generated app name and qb's SQLite grammar and default datasource had therefore never taken effect. The file is `Coldbox.bx` with `variables.` and a real-boot spec reads the settings back.
- **The Docker recipe was built and run.** The Docker target builds from `.build` into `/srv/bxapp` (`ENV APP_DIR=/srv/bxapp`, `BOXLANG_HOME=/srv/bxapp/runtime`, host `0.0.0.0`). It is not `/app`: that is also the ColdBox mapping name, so BoxLang resolved `/app/app/config/bxai-settings.json` through the mapping to `/app/app/app/config/...` and the first request failed with "Failed to load application descriptor"; do not install an app under a folder named `/app`. In the container `/__bxagents/health`, `/chat/` and its assets answer 200 and `/config/...`, `/project/Agent.yml`, `/app/config/bxai-settings.json` and `/runtime/boxlang.json` answer 404. Not verified: a model call from the container.
- **The SSE note was corrected.** `AGENTS.md` and the `serve` comments said the web runtime's whitespace compression removes the blank line that ends each SSE frame, so a native stream carried no terminators. Measured on BoxLang and boxlang-miniserver 1.19.0, it does not: `/__bxagents/stream` has 14 terminators, 14 frames and 8 content deltas with the setting on and off (`route().toSSE()` 5 and an `SSE()` page 4, the same both ways). Only a hand-written `writeOutput( "...\n\n" )` stream loses them (0 against 3). The vendored `runtime/boxlang.json` keeps the setting off as a safety net.
- **Smaller fixes found on the way.** `getSystemSetting()` keeps its first answer per key for the life of the process (so tests pass the module folder as an option and never change `BXAGENTS_MODULE_DIR` mid-process); `directoryDelete( path, true )` follows links, and a `test` run had emptied the built module through the link it used: it, and `clean`, now delete without following links. `aiToolRegistry().scan()` expands its dotted path against a mapping, so the scan is `app.tools`, a mapping path and not one relative to the app; `skillsDirectory` is `/app/skills`. A project under a path with a space does not start (the `boxlang-miniserver` launcher script does not quote `BOXLANG_HOME`, for any layout).
- **Layered settings:** the person who installs an agent can override and add to any of its settings, not only `tui:`, from two files that are both called `Agent.yml`: `~/.bxagents/Agent.yml` for every agent and `~/.bxagents/<agent>/Agent.yml` for one. They apply when `bxAgents build` runs and again when a built app starts, from one merge (`SettingsLayers`), over the author's `Agent.yml`, `environments:` and `boxlang.json`. A map merges, a plain value or a list replaces, `key+:` appends (a list, or text such as `instructions`), `key-:` removes entries from a list and `key: ~` removes the key. `chat:` is valid only in a person's file. Everything except `name`, `data.home` and `environments` can be set. What a built app can not change without a rebuild (`agentApi`, `gatewaySession`, `routines`, `subAgents`, `data`) is reported at start with its file. `/info` lists each setting that came from a person's file, and `/settings model ollama/qwen3 [--global]` writes any setting to the agent's own file or the one for every agent, keeping the rest of the file. Extension values now follow the same rule: the person's win over the project's. See [layered settings](docs/conventions/layered-settings.md).
- **`.yml` for the connector catalog too:** the files under `src/main/bx/catalog/connectors/` are `<id>.yml` (were `<id>.yaml`), and the catalog check and the packaging read that name. `Agent.yaml` is not accepted as the agent's file by the admin file view either. The docs site's own `bxsites.yaml` and `docs/data/` files keep their names.
- **One file name:** the author's file, the person's file for every agent (was `bxAgents.yml`) and the person's file for one agent (was `settings.yml`) are all `Agent.yml`. `Agent.yaml` is no longer read. The old names are dropped with no fallback.
- **Terminal chat settings:** one registry of settings for how the chat looks and behaves (`fullscreen`, `header`, `spacing`, `theme`, `animations`, `thinking`, `tools`, `markdown`, `menuRows`, `notify`, `terminalTitle`, plus the message box's `prompt` and `widgets`), in the same `tui:` block of four places: the flag of one run (`--inline`, `--fullscreen`), the agent's own `Agent.yml` in its data home, your `~/.bxagents/Agent.yml` (the fallback for every agent), and the project's `Agent.yml`, then the default. `/settings` opens a panel that shows each value and where it comes from, changes it with the arrow keys and saves it, after asking once for each file, and `/settings name value [--global]` does it from the message box. Only the `tui:` lines of a file are edited
- **The chat opens full screen:** it clears the screen, draws a header at the top with the bxAgents icon in braille characters (the style of the BoxLang installers' banner), the name and the agent, the version and model, a line each for the skills, extensions, connectors, gateways and MCP servers the agent has, and the keys, and keeps the message box at the bottom with a footer of the folder and branch, the context and the profile. `header: compact` or `hidden` shrink the header, `--inline` or `fullscreen: false` keep the old inline behaviour. The top bar of the box now says only who is writing by default, so the default widgets are none at the top and `folder`, `git`, `ctx` and `profile` at the bottom
- **bxAgents ships its own skills:** six skills inside the module (`bxagents-build-agent`, `bxagents-tools-and-skills`, `bxagents-subagents-routines`, `bxagents-gateways-connectors`, `bxagents-chat` and `bxagents-operate`) are given to every agent as skills available on request: only a name and a description are in the context until the model asks for one. A skill of the project with the same name wins, the agent's own cannot take their names, `/skills` and `GET /skills` list them with the origin `bxagents`, and `skills.builtin: false` in `Agent.yml` leaves them out
- Initial development and setup of the project.
