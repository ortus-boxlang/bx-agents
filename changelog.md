# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

- **Changed: every command line verb describes itself, and a base class does the shared work.** A verb says what it is in `meta()` (group, usage, actions, options, examples) and does its work in `handle()` or `handle<Action>()`; `BaseVerb` checks the project root, picks the action, answers `--json` once and gives the helpers for options, results and output. The help, the shell completions and the usage, actions and options of `docs/cli-reference.md` are made from `meta()`, so a flag is described once. What a person sees is the same: a snapshot of every help page pins it.
- **Changed: the Embeds page is a list, and making or changing an embed is a page of its own.** The list (`/embeds`) has a search (name and websites), a state filter (All, On, Off, Expired), a switch to turn each embed on or off at once, and Edit and Delete. New (`/embeds/new`) and Edit (`/embeds/<id>`) are separate pages, each with its own handler action and view; saving a new embed keeps the page, which is then the edit of that embed. Leaving with changes that are not saved asks first.
- **New: delete an embed** (`POST /embeds/delete`, `bxAgents embed delete --id=...`, and Delete on the page). It removes the embed for good, with its signing key and its counters; turning it off stays the way to keep one. The API has 89 routes now.
- **Fixed (from a review of the embeds code):** a visitor is told one fixed sentence when a turn fails, not the provider's or the engine's message; the tool filter allows no tool when a request object cannot say what it is; updating only `look`, `limits` or `target` keeps the fields it does not send; a `429` of an embed carries `Retry-After`; a colour or tool name with a line break after it is refused; an origin written with the scheme's own port (`:443`, `:80`) is stored without it, as a browser sends it.
- **New: Gmail, Google Calendar and Google Drive, with a sign in BxAgents does itself.** Each person signs in on Google's own page from the web app or the terminal and the agent calls Google's MCP servers with their token (Google's terms for agents require its MCP servers). A connector file can now give the addresses of its sign in (`endpoints`) and extra parameters (`params`, such as `access_type: offline`) on an `app: own` method, and `OAuthApp` does the authorization code flow with PKCE, keeps the tokens sealed per person in the vault, renews them and revokes them on disconnect. The admin sets `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` once. A connector can say `onDisconnect: purge`: the agent notes which conversations used it, and when the person disconnects it the answers in those conversations are replaced by a note (their own messages stay). Also fixed: the tools drawer of a public (no sign in) server listed its tools through the sign in side and failed.
- **New: four more ways a connector can ask you in, and 9 more connectors (35 in all).** A token can go in a header of its own (`header` and `prefix` on a bearer method: Bigdata.com, Meltwater, Metricool, Daloopa, Wix). A host can be chosen from a fixed list (`https://{site}/mcp` with an option of `target: host` and its `choices`: Datadog, and Mixpanel's US, EU and India regions). A web connector can be a public server with no sign in (`auth: none`: Excalidraw). A sign in can use an app of the admin's own (`app: own` with `envVars` naming the client id and secret, read when the agent starts and never written to a file: Slack, Asana, Box, Canva, HubSpot, X Ads); until it is set the connector says an admin has to set it up. The web page, the terminal and `connectors show` explain each. Connectors with a token in another header or a host list are offered as connectors only, not by `--mcp`.
- **New: 17 more connectors, and the catalog is grouped.** Added Linear, Calendly, ClickUp, Gamma, HyperFrames by HeyGen, Netlify, Vercel, Mixpanel (US region), Buffer, Metricool, Zapier, Wix, Whop, RingCentral Chat, RingCentral Phone, Daloopa and S&P Global, each checked against the service's own documentation and its server (address, sign in and dynamic client registration), so the catalog has 26. Every connector file now has a `category` (Developer, Productivity, Sales, Finance, Analytics, Microsoft 365, Social Media, Advertising or Apps). `GET /connectors` returns `categories` and a `category` on each row; the web page shows one section per category, `bxAgents connectors`, `connect` and `/connect` print a heading for each, and the docs page is written by category. The wizard's "Leave out any connectors?" list and `--connectors` now cover every connector, including the ones a person only signs in to (it listed only those with a token before). Icons of the connector files are checked against the web app's sprite by a spec.
- **New: `new` can set up LM Studio and llama.cpp.** Both are in the provider list of the wizard (no key). Each asks for the model id the server lists and the address it listens on, with the usual one filled in (`http://127.0.0.1:1234/v1` and `http://127.0.0.1:8080/v1`), writes the model as `openai-compatible/<id>` and the address under `providers:` in `Agent.yml`. Without the wizard: `--model=openai-compatible/<id> --base-url=<address>`.
- **New: `look.icon` for an embed, and `agentApi.embeds: false`.** An admin picks the widget's button icon from five built-in glyphs (`chat` is the default, so nothing changes for an embed that has none). `agentApi.embeds: false` is a master switch that writes no embed route, hides the Embeds page and leaves the embed operations out of the OpenAPI document.
- **New: the Embeds page of the web app (Admin, next to Gateways).** A list of embeds with their state, and an editor with a fieldset each for the agent, the look and text, the tools a visitor may use (everything unticked is off), the allowed websites (chips that refuse a wildcard, a path or a non-origin; at least one) and the limits. A preview on the right is the real widget (`<bx-agent mode="preview">`, drawn from the form, no network), the snippet panel gives HTML, iframe, web component and curl with a note and a Copy button each, and the last seven days are real counters or "No visits yet". Save, Disable and Rotate key (both ask first). Admin only, from the new `embeds` capability. Browser tests cover the page and visitors of other websites from real servers on other ports; axe checks the page in light, dark, desktop and phone.
- **New: the embed widget and the hosted page.** `widget.js` is a plain-JavaScript `<bx-agent>` element (launcher and panel, or the whole page with `mode="page"`) with the look from `/config`, a streamed answer, a transcript kept in `localStorage`, and the accessibility the spec asks for (focus management, Esc, a polite status region, reduced motion, colour contrast chosen from the embed's colour). One `<script data-embed>` tag adds it. The hosted page (`/embed/<id>/frame`) runs on the agent's own origin, which is now always accepted, and a same-origin `GET` is recognised by `Sec-Fetch-Site`. Found by running it in a browser: the hosted page drew nothing before that.
- **New: the embed filter.** A middleware attached to every agent the build makes. For a turn of an embed's visitor (`TurnRunner` sets `usageMetadata.embedId` from the verified session) it takes the tools the embed does not list out of what the model is offered, and refuses a call to one that is not listed; any other turn is left alone and reads no database. It follows the embed's list as the admin changes it and allows no tool for an embed that is off, expired or unreadable. Measured on a served app: the visitor's model was offered only `docs_search`, the admin's four tools, and a `delete_all` the visitor asked for did not run.
- **New: the public side of embeds (increment 1).** `GET <api>/embed/widget.js`, `GET /embed/<id>/config`, `POST /embed/<id>/session`, `POST /embed/<id>/events` (an SSE stream, run in this process through the same `TurnRunner`), `POST /embed/<id>/cancel`, `GET /embed/<id>/history` and `GET /embed/<id>/frame` (with `Content-Security-Policy: frame-ancestors` for the embed's websites). They sit outside the token gate and the address guards, with their own checks: the embed is live (an unknown, off or expired one all answer `404`), the `Origin` is one of its websites (`403`, counted), a session signed with the embed's own key and bound to the website it was issued to (`401`), a per-visitor limit per minute, a daily cap and a message length limit. A visitor is a `Caller` of the new least-privilege scope `embed` (`v:<visitor>`), made only from a verified session; no regular route accepts one. Conversation ids are made by the server from the visitor. `build.gradle` now packs `models/embed/*.js` into the module. Not yet: the embed filter middleware (tool list), the real widget, the Embeds page.
- **New: embeds, the store, the admin API and `bxAgents embed` (increment 1 of the agent on another website, for anonymous visitors).** An embed is a record in the agent's database (`embeds` and `embed_usage`, schema version 15): the look, the tools a visitor may use, the websites that may show it, three limits and a signing key of its own that no route returns. `EmbedService` validates every field on save and says every problem at once (an origin is exactly scheme, host and optional port: no wildcard, no path, `null` refused; at least one is required). The admin routes `GET/POST /embeds`, `GET /embeds/get`, `POST /embeds/update`, `POST /embeds/rotate`, `GET /embeds/snippets` and `GET /embeds/usage` are admin only and bring the API to 88 routes; `bxAgents embed create|list|show|disable|rotate` does the same from a terminal. The public routes, the widget and the Embeds page come next. Spec: [Embeds](docs/conventions/embeds.md).
- **Fix: a project that hosts an MCP server (`mcp/`) built but failed on every request.** The generated `Application.bx` registered the server's tools with `aiToolRegistry().get( name )` before `aiToolRegistry().scan( "app.tools" )` had run, so the served app answered `No item found in registry for key [search]` (`examples/mcp-agent` and `examples/advanced-agent` both did). The scan now comes first when a project hosts an MCP server. `verifyExamples` only builds, so it never saw this; a spec checks the order.
- **Fix: `/skills` ran a long skill name into the next column** (`bxagents-gateways-connecbxagents`). The name column is now as wide as the longest name.
- **Examples: a demo script for a local model, and fixes found while running them.** `examples/demo.md` is the presenter's script for four live demos (the smallest agent, a team on two models, the web app, the API and MCP) against LM Studio, with the exact `Agent.yml` lines (`providers: openai-compatible: options: baseURL`), a pre-flight, recovery lines and a scripted fallback (`examples/demo-model.json`). `tools/demo/fakellm.bxs` answers `GET /v1/models`. `examples/api-agent/client.bxs` makes a new token name on every run (a second run failed with HTTP 409), and `examples/webui-agent/README.md` describes the current web app (the page is `/chat`, not `/chat/index.html`).
- **Fix: the web chat talked to the main agent when a sub-agent's conversation was not among the 25 it lists.** Opening a sub-agent's conversation from the Conversations page (or reloading the chat) worked out the owner from the list page alone, so a conversation older than the newest 25 was sent without its `agent` and every message answered `conflict: This conversation belongs to helper`. `GET /history` now also answers `agent`, the agent the conversation belongs to (new `Conversations.ownerOf`, owner-checked like the rest of the route), and the chat takes it from there. Covered by a spec and an end-to-end test against a sub-agent of the UI dev agent.
- **Fix: `GET /routines?all=1` returned only the admin's own routines, and a member asking for all was ignored.** The generated handler read `all` with a flag that accepts only a real JSON `true`, so the query value `1` (what the Routines page and the contract say) counted as false, while `?all=true` worked. Query flags (`all` on `/routines` and `/sessions`, `facets`) now share one `queryFlag()`: `1`, `true` and `yes` in any case are on, `0`, `false`, `no`, blank or anything else are off, which is what `/sessions` already accepted. A member who asks for all on `/routines` now gets `403 forbidden`, as on `/sessions`. Body flags (`all`, `apply` of `/routines/reports/clean`) still need a JSON boolean, and a member who does not ask for all sees what they saw before.
- **Fix: the Memory page's "Clear all conversation memory" said it would forget your conversations but cleared everyone's.** For an admin the button, the confirmation and the count came from the admin's own `GET /sessions`, while `POST /memory/clear` with `all: true` clears every conversation of every user. The button now reads "Clear everyone's conversation memory", the confirmation says it is everyone's and gives the real totals ("all 12 conversations of all 4 people", from `GET /sessions?all=1`; "of everyone" when more than 100 conversations make the people count unknown), and an admin with no conversations of their own sees the button when others have some. A member never sees it.
- **Fix: the Conversations page could delete rows you could not see.** The selection survived a search, a filter, a page change and a page size change, so after hiding the selected rows the bar still said "2 selected" and Delete selected asked "Delete 2 conversations?". The selection now clears whenever the visible set changes, and the confirmation names the conversations (the first five, then "and N more").
- **Security: a caller can no longer cancel or steer somebody else's run.** `POST /cancel` and `POST /steer` passed the client's thread id straight to bx-ai, which keeps its runs by thread id alone, and the client chooses that id (the web page's fallback on plain http is `"t-" + Date.now() + ...`), so any signed-in member who named another person's id could stop their run or add text to it, and two callers who picked the same id shared one slot. `TurnRunner` now hands bx-ai `u:<caller id, URL-encoded>:<thread id>` for every turn, cancel, steer, pending and resume, so a caller can only reach runs it started; the frames and answers the client receives carry its own id. The caller id is URL-encoded so one containing a colon cannot collide with another caller's scope. There is no admin override. The routines' report and notes tools, the usage log and the terminal's stop and steer read or build the same id. **A run paused for approval at upgrade time cannot be resumed**: its checkpoint is stored under the old id, so `/resume` finds nothing. Ask again.
- **Fix: `bxAgents models test` failed on the default model of an `openai-compatible` or Docker Model Runner project** with "Provider [OpenAICompatible] is not supported". bx-ai reports such a provider by its display name, and the probe passed that name on instead of the provider id. The probe now maps the name to its id first.
- **Fix: `bxAgents test` printed `Error: -1` and exited 0 when a project had no `environments.test`.** The agent could not be built for the test run and TestBox recorded that as a bundle error the runner never read. The run now says which bundle could not start and why, explains how to add `environments.test` (or a `test()` in `Agent.bx`), and exits 1.
- **Fix: dates in `routines reports`, `logs`, the `/routine` command and the logs' last-error time were wrong.** They used the CFML mask `yyyy-mm-dd HH:nn`, but BoxLang reads `mm` as minutes and `MM` as the month, so 24 November 2026, 13:07 printed as `2026-07-24 13:00`. They now use `yyyy-MM-dd HH:mm`, and the docs examples that used `'yyyy-mm-dd'` say `'yyyy-MM-dd'`. A spec fails if either wrong mask comes back.
- **Breaking for contributors: building the module needs Node 24, and the web app's Vite build is no longer committed.** `src/main/bx/bxagentsui/includes/build/` is git-ignored. `./gradlew uiBuild` (`npm ci`, then `npm run build` in `ui/`) makes it, is skipped when `ui/` has not changed, and `createModuleStructure` depends on it, so `shadowJar`, a release and a snapshot always ship a fresh web app. There is no skip flag: a missing Node or npm, or a major other than 24, fails the build with what to install. `ui/.nvmrc` and `engines` pin Node 24, every workflow that runs Gradle sets up Node 24, and the `git diff --exit-code` freshness check is gone. `npm run stack` stops with a message when the build is missing. A generated project still never needs Node.
- **Security: a request can no longer make the server read an image file.** `images: [ { path } ]` in a turn request went to `MessageBuilder`, which embedded any png, jpg, gif or webp the server could read and answered `There is no image file [path]` for one it could not. `TurnRunner` now takes `images` only when it was built with `localImages`, which only the in-process terminal does (a caller's `source` comes from a request header, so it is no proof). Over HTTP, from a gateway or a routine the key is dropped and logged by name; pictures travel as `attachments` with base64 data.
- **Security: a caller can no longer run a tool without its approval, or pick the model.** `TurnRunner.prepareTurn` passed the caller's `options` and `params` to bx-ai whole. bx-ai reads `options._resumeContext` and, with it, runs the tool calls the request carries without reaching the approval middleware, so a caller with `chat` scope could run any approval-gated tool (for example `skill_save`, a shared and persistent prompt injection) with one POST to `/invoke`, `/stream`, `/batch` or `/events`. The same pass-through let `params.model` and `options.apiKey` override the `agentApi.profiles` list. A new `TurnOptions` keeps only `options.profile`, and for `params` everything the model accepts except `model`, `messages`, `contents`, `system`, `tools` and any `_` key at any depth (the body sent to the provider is `{ model, messages }` plus `params`, so those would replace the model, the conversation, the prompt or the tool set). The rest is dropped without an error and its names are logged. Nothing that this repo sends needed another key: the web page, `AgentApiClient`, the terminal and the routines send `options.profile` at most. Docs: "What a turn accepts" in the Agent API guide.
- **The course grows from 20 to 29 lessons, and builds one agent.** "Introduction to BxAgents" now follows Acme support from a scripted model that needs no key (`tools/demo/fakellm.bxs`) to a packaged agent, with nine new lessons (a model that needs no key, approvals, memory and notes, routines and reports, users, roles and tokens, the vault, layered settings, logs usage and backups, a capstone), a rewritten web app lesson that comes earlier, and a checkpoint at the end of each lesson. Lesson files keep their names, so URLs and saved progress are unchanged; the order is `docs/data/courses.yaml` and titles carry no lesson number. `tools/course/` has the checker (`boxlang tools/course/check-course.bxs`: static checks, and a replay of every lesson's commands against the scripted model that also keeps the checkpoints honest) and the kit a learner downloads. The scripted model gained `noTool`, `{tools}` and a `--script` that is read from the current folder first.
- **Breaking: a built app is `app/` and `public/`, like the ColdBox BoxLang template.** `bxAgents build` writes `.build/app` (the generated code), `.build/public` (the web root and the only folder a server serves), `.build/lib` (ColdBox and its modules), `.build/runtime` (the engine config, the `bx-agents` module with internal alias `bxagents`, and the BoxLang home), `.build/boxlang_modules` and `.build/miniserver.json`. **Rebuild every existing app**: `serve` refuses a build made before this layout and says so. `.build/app` is no longer the web root, so anything that served it (a script, a Dockerfile of your own, a `.bxaignore` whose patterns were relative to `.build/app`, which are now relative to `.build`) has to follow. The template is carried in the module as a pinned snapshot (`templates/coldbox-boxlang`, version and commit in its `VERSION`, refreshed with `tools/refresh-coldbox-template.sh`) and the build never reads the network.
- **The exposure fix: nothing but `public/` is served.** The old layout served the whole app folder, so `/config/agent-settings.json`, `/project/Agent.yml`, `/agent/instructions.md` and a listing of `/config/` and `/skills/` answered 200 to anyone who could reach the port, token or not. All of them answer 404 now, and so does every other file outside `public/`. The server now runs only `index.bxm` (a `passPredicate` in `miniserver.json`): a `.bx` class under the app, or a ColdBox module, is no longer executed by address (it answered 200 with an empty body). An address nothing routes is a small JSON `404` and not ColdBox's 500 error page. Covered over HTTP by `ServedLayoutSpec`. `public/includes/` lists its file names (the server turns directory listing on in code and `miniserver.json` has no key for it); it holds only what the browser loads.
- **Only the `bx-agents` module (internal alias `bxagents`) is loaded.** `serve` used to add the machine's own module directory to the served app, which loaded every module installed there. The module is now copied into `.build/runtime/modules/bx-agents` (to a work folder, then renamed, and skipped while a stamp of its `box.json` and jars is unchanged), `runtime/` is the BoxLang home, and no module directory of the machine is named anywhere: the `test` verb's child loads the module alone through a link as well. A decoy module in `~/.boxlang/modules` does not load in the served app, and does load in a server without that home (spec).
- **`public/Application.bx` is derived from the template's and changed.** It ends as a thin class that extends the generated base `app/bxagents/Application.bx`, or is your own root `Application.bx` pointed at that base (`bxagents.Application` is still the name you write). The base carries what the template's file does (the `COLDBOX_*` settings, the bootstrap call, `loadColdbox()`, `onRequestStart()`) plus the app name, sessions, datasource, schedulers, the data home and the registrations; the template's `onApplicationEnd`, `onSessionStart`, `onSessionEnd` and `onMissingTemplate` are not carried. Settings and the hooks `before()`, `after()` and `beforeRequest()` (and the lifecycle methods themselves) are what you can customize. See [Application.bx](docs/conventions/application-bx.md).
- **Generated config that never applied, now applies.** The ColdBox config was written as `config/ColdBox.bx` (ColdBox loads `config/Coldbox.bx`, so on a case-sensitive file system it was never loaded) with `coldbox = {` and `moduleSettings = {` (an unscoped assignment is local to `configure()` in BoxLang). The generated app name and qb's SQLite grammar and default datasource had therefore never taken effect. The file is `Coldbox.bx` with `variables.` and a real-boot spec reads the settings back.
- **The Docker recipe was built and run.** The Docker target builds from `.build` into `/srv/bxapp` (`ENV APP_DIR=/srv/bxapp`, `BOXLANG_HOME=/srv/bxapp/runtime`, host `0.0.0.0`). It is not `/app`: that is also the ColdBox mapping name, so BoxLang resolved `/app/app/config/bxai-settings.json` through the mapping to `/app/app/app/config/...` and the first request failed with "Failed to load application descriptor"; do not install an app under a folder named `/app`. In the container `/__bxagents/health`, `/chat/` and its assets answer 200 and `/config/...`, `/project/Agent.yml`, `/app/config/bxai-settings.json` and `/runtime/boxlang.json` answer 404. Not verified: a model call from the container.
- **The SSE note was corrected.** `AGENTS.md` and the `serve` comments said the web runtime's whitespace compression removes the blank line that ends each SSE frame, so a native stream carried no terminators. Measured on BoxLang and boxlang-miniserver 1.19.0, it does not: `/__bxagents/stream` has 14 terminators, 14 frames and 8 content deltas with the setting on and off (`route().toSSE()` 5 and an `SSE()` page 4, the same both ways). Only a hand-written `writeOutput( "...\n\n" )` stream loses them (0 against 3). The vendored `runtime/boxlang.json` keeps the setting off as a safety net.
- **Smaller fixes found on the way.** `getSystemSetting()` keeps its first answer per key for the life of the process (so tests pass the module folder as an option and never change `BXAGENTS_MODULE_DIR` mid-process); `directoryDelete( path, true )` follows links, and a `test` run had emptied the built module through the link it used: it, and `clean`, now delete without following links. `aiToolRegistry().scan()` expands its dotted path against a mapping, so the scan is `app.tools`, a mapping path and not one relative to the app; `skillsDirectory` is `/app/skills`. A project under a path with a space does not start (the `boxlang-miniserver` launcher script does not quote `BOXLANG_HOME`, for any layout).
- **Layered settings:** the person who installs an agent can override and add to any of its settings, not only `tui:`, from two files that are both called `Agent.yml`: `~/.bxagents/Agent.yml` for every agent and `~/.bxagents/<agent>/Agent.yml` for one. They apply when `bxAgents build` runs and again when a built app starts, from one merge (`SettingsLayers`), over the author's `Agent.yml`, `environments:` and `boxlang.json`. A map merges, a plain value or a list replaces, `key+:` appends (a list, or text such as `instructions`), `key-:` removes entries from a list and `key: ~` removes the key. `chat:` is valid only in a person's file. Everything except `name`, `data.home` and `environments` can be set. What a built app can not change without a rebuild (`agentApi`, `gatewaySession`, `routines`, `subAgents`, `data`) is reported at start with its file. `/info` lists each setting that came from a person's file, and `/settings model ollama/qwen3 [--global]` writes any setting to the agent's own file or the one for every agent, keeping the rest of the file. Extension values now follow the same rule: the person's win over the project's. See [layered settings](docs/conventions/layered-settings.md).
- **`.yml` for the connector catalog too:** the files under `src/main/bx/catalog/connectors/` are `<id>.yml` (were `<id>.yaml`), and the catalog check and the packaging read that name. `Agent.yaml` is not accepted as the agent's file by the admin file view either. The docs site's own `bxsites.yaml` and `docs/data/` files keep their names.
- **One file name:** the author's file, the person's file for every agent (was `bxAgents.yml`) and the person's file for one agent (was `settings.yml`) are all `Agent.yml`. `Agent.yaml` is no longer read. The old names are dropped with no fallback.
- **Terminal chat settings:** one registry of settings for how the chat looks and behaves (`fullscreen`, `header`, `spacing`, `theme`, `animations`, `thinking`, `tools`, `markdown`, `menuRows`, `notify`, `terminalTitle`, plus the message box's `prompt` and `widgets`), in the same `tui:` block of four places: the flag of one run (`--inline`, `--fullscreen`), the agent's own `Agent.yml` in its data home, your `~/.bxagents/Agent.yml` (the fallback for every agent), and the project's `Agent.yml`, then the default. `/settings` opens a panel that shows each value and where it comes from, changes it with the arrow keys and saves it, after asking once for each file, and `/settings name value [--global]` does it from the message box. Only the `tui:` lines of a file are edited
- **The chat opens full screen:** it clears the screen, draws a header at the top with the bxAgents icon in braille characters (the style of the BoxLang installers' banner), the name and the agent, the version and model, a line each for the skills, extensions, connectors, gateways and MCP servers the agent has, and the keys, and keeps the message box at the bottom with a footer of the folder and branch, the context and the profile. `header: compact` or `hidden` shrink the header, `--inline` or `fullscreen: false` keep the old inline behaviour. The top bar of the box now says only who is writing by default, so the default widgets are none at the top and `folder`, `git`, `ctx` and `profile` at the bottom
- **bxAgents ships its own skills:** six skills inside the module (`bxagents-build-agent`, `bxagents-tools-and-skills`, `bxagents-subagents-routines`, `bxagents-gateways-connectors`, `bxagents-chat` and `bxagents-operate`) are given to every agent as skills available on request: only a name and a description are in the context until the model asks for one. A skill of the project with the same name wins, the agent's own cannot take their names, `/skills` and `GET /skills` list them with the origin `bxagents`, and `skills.builtin: false` in `Agent.yml` leaves them out
- Initial development and setup of the project.
