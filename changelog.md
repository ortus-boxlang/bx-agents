* Added an agent testing framework: `bxAgents new` now scaffolds a ready-to-run `tests/` folder, and a new `test` verb runs a project's `tests/specs` via TestBox against a fresh child BoxLang process. `BaseAgentSpec` builds the project's agent against the mock provider by default and adds `mockResponses()` plus custom matchers (`toContainText`, `toHaveCalledTool`, `toHaveReceivedMessage`)

* Full-framework review pass. Fixed a security bug: an `http` gateway's `secret` was embedded as a plaintext literal in generated `Application.bx` source and shipped unredacted inside the packaged `.bxa` - gateways now declare `secretEnvVar` (the NAME of an environment variable), resolved live via `getSystemSetting()`, never written to generated source. Applied the same secrets-stay-external convention to `ftp`/`sftp` (`passwordEnvVar`/`passphraseEnvVar` replace `password`/`passphrase`) for consistency with `docker`/`digitalocean`, which already resolved secrets from env vars
* Fixed several "passed validation cleanly, then crashed mid-generation" gaps by moving each check into `ProjectValidator`'s Phase 3, consistent with this project's own "collect every error before generating" promise: a schedule's `action` presence, cron-shape support (`ProjectValidator` now calls a new `SchedulerGenerator.isSupportedCron()`, reusing the generator's own translation logic instead of a second, independently-drifting regex), and the ROOT project's own `subAgents` references (previously excluded from the unknown-subagent check, so only nested subagents' bad references were caught)
* Fixed a bug where a subagent's own environment-specific `Agent.bx` overrides always resolved against its default environment, ignoring whatever `--environment` the whole build was invoked with - `cliEnvironment` is now threaded through to every subagent's own config resolution
* Fixed a bug where a bare `model` value (a core provider name with no model, e.g. `"openai"`, or a `models/` entry name, e.g. `"summarizer"` - both explicitly validated as legal) crashed `ColdBoxAppGenerator` mid-generation; it now resolves both shapes correctly, including reading a referenced `models/` entry's own `{provider, model}` config
* Renamed `SshTarget`'s `user` config field to `username`, matching `ftp`/`sftp`'s field name for the same concept; `ssh`/`docker` targets now wrap a missing/failed local process launch (`scp`, `ssh`, `docker`) in a clear `BxAgents.DeployFailed` error instead of an opaque Java exception
* Corrected several stale documentation claims found during the review: `schedules.md`'s validation-phase description, `mcp.md`'s missing `cors` field, `deploy.md`'s missing `timeout` field for `ftp`/`sftp`, `subagents.md`'s stale unknown-subagent error wording, `gateways.md`'s fabricated `cli`-gateway-backs-`chat` claim, and `agent-bx.md`'s fabricated third environment-precedence tier
* Fixed the same "validated but crashes at generation" gap for a subagent's own `model` field: `validateModelProvider()` was only ever called against the ROOT project's config, so a subagent with an unknown provider or an unmatched `models/` reference passed validation cleanly and only threw mid-generation. It's now validated per-subagent too, with errors clearly attributed to the offending subagent
* Added complete DocBox-style documentation comments (class-level + `@param`/`@return` on every function) across every `.bx` source file, and filled in the remaining Javadoc gaps in `BxaPackager.java`'s private helpers - a full audit found 109 undocumented functions and 32 with incomplete `@param` tags; both counts are now zero
* `new` now runs `box install` inside the scaffolded `tests/` folder automatically, so `bxAgents test` works immediately without a separate manual `cd tests && box install` step. Best-effort: a missing `box`/failed install doesn't fail `new`, it just tells you to run it yourself. Opt out entirely with `--skipInstall`
* `inspect` gained a `--json` flag, printing the raw manifest instead of the human-readable summary, for scripting
* Added a new `invoke` CLI verb - a single, non-interactive turn against a built agent (submit one message, print the response, exit), for scripting/CI where `chat`'s real-TTY requirement is a hard blocker. Defaults to an in-process call (no server needed); `--server` instead launches a real, throwaway `boxlang-miniserver`, sends the message over real HTTP through the project's `toAi()`-exposed route, and tears the server back down - exercising the actual served path instead of the in-process shortcut. `--json` wraps the response as `{"response": "..."}`
* Fixed a bug where `serve` (and `invoke --server`, which reuses it) never set a `serverHome` in the generated `miniserver.json`, so every served BX Agents project on a machine defaulted to sharing the same global `~/.boxlang` runtime home - its compiled-class cache, and critically any machine-level `~/.boxlang/config/boxlang.json` override, applying to every served project equally. `serve` now scopes this to `.build/runtime`, which `clean` already sweeps for free since it wipes `.build` wholesale. This only reaches the two verbs that spawn their own separate JVM process (`serve`/`invoke --server`) - `chat`/`build`/`test`/default `invoke` run in-process and inherit whatever home the already-running `bxAgents` process itself resolved before any of our code ran, which nothing at the verb level can change retroactively (see known-limitations.md)
* `new` now scaffolds a `.env` declaring `BOXLANG_HOME=.build/runtime` (mirroring `ortus-boxlang/bx-ai-intro`'s own `.env` convention, and matching `serve`'s own scoped path) plus a `.gitignore` (`.build/`, `dist/`, `.env`) - confirmed directly against the real BoxLang runtime jar that `BOXLANG_HOME` is a genuine environment variable read by `BoxRunner` itself (not just miniserver) before `BoxRuntime` initializes, for every invocation. Whether this reaches the in-process verbs depends on whether your BoxLang install auto-loads `.env` from the project directory - confirmed the raw runtime jar does *not* do this itself, so this is a real, honestly-documented "depends on your install" gap, not a guarantee (see known-limitations.md)
* **Reworked `schedules/` entirely.** It no longer holds a BX Agents-specific `{ cron, action }` config translated into ColdBox's narrow frequency-method DSL (which only supported single exact values - no lists, ranges, or a cron combining day-of-month and day-of-week). It now holds one real, hand-written `schedules/Scheduler.bx`, extending ColdBox's own `ColdBoxScheduler`, passed through into the build untouched - the full native ColdBox scheduler API (`.cron()`, `.withNoOverlaps()`, `.startOn()`/`.endOn()`, `.when()`, hooks, etc.), no BX Agents translation layer to be limited by. To support this, every agent in a project's tree - the root project's own `Agent.bx` and every `subagents/*` entry, however deeply nested - is now registered in the generated `config/WireBox.bx` under its own declared `name`, not just the fixed root `"GeneratedAgent"` alias, so a schedule reaches whichever agent it wants with a plain `getInstance( "TheAgentName" )`. Since `name` is now also a WireBox binding key, `build` validates it's unique across the whole tree (two agents silently sharing the `"BxAi"` default now fails loudly instead of one WireBox mapping silently shadowing the other). `build` also warns if `schedules/` exists but has no `Scheduler.bx` in it (e.g. a leftover file from the old convention), so a schedule that quietly stopped working is at least visible
* `build` gained a `--verbose` flag: prints one line per build phase live as it runs - resolved config, discovered counts, validation warnings, per-generator output (interceptor split, gateway/MCP registration counts, which agents ended up registered in `config/WireBox.bx` and under which names, whether a `schedules/Scheduler.bx` was found), and a final timing line. `BuildPipeline.build()` itself takes this as an `onProgress` callback (defaulting to a no-op) rather than hardcoding `println()`, so it costs nothing when `--verbose` isn't passed and is unit-testable by passing a collecting closure instead of capturing real stdout
* Followed a real, upstream bx-ai rename: `gatewayRegistry()` is now `aiGatewayRegistry()` (confirmed against bx-ai's real `development` HEAD - `bifs/gatewayRegistry.bx` was deleted outright, no back-compat alias). `GatewayGenerator` now emits `aiGatewayRegistry().register( aiGateway( ... ) )` for every channel-adapter `gateways/*` entry. Since bx-ai hasn't cut a release yet, this is a straight rename, not a compat shim - see known-limitations.md for the (temporary) snapshot-artifact lag this surfaced
* **Added the first push-style chat-platform gateway: Telegram**, plus the `GatewaySession` wiring that makes push-style gateways actually dispatch inbound messages to the agent. A `gateways/*` entry with `type: "telegram"` (`botTokenEnvVar` required, same secrets-stay-external rule as `http`'s `secretEnvVar`) registers a `TelegramGateway` (long-poll inbound via Telegram's `getUpdates`, HTTP outbound with automatic chunking at Telegram's 4096-char message limit, inline-keyboard-button human-in-the-loop approval flows). Any project with at least one push-style gateway also gets a generated `interceptors/GatewaySessionBootstrap.bx`, building a single bx-ai `GatewaySession` (bundling every push-style gateway, bound to the project's root agent) and starting it once ColdBox itself has finished loading - controllable via a new optional `gatewaySession: { policy, maxQueueDepth }` block on `Agent.bx`. See `docs/conventions/gateways.md`'s new "Push-style gateways" section
* Rather than inventing a new background-loop primitive, push-style gateways reach the app's own live ColdBox scheduler singleton (`appScheduler@coldbox` - the same one a hand-written `schedules/Scheduler.bx`, if present, runs under) and register their own named task(s) into it dynamically, via a new shared `ScheduledGatewayBase` (`models/gateways/ScheduledGatewayBase.bx`) every push-style gateway extends. One shared scheduler, every gateway registering its own tasks into it - never one scheduler per gateway, and never in conflict with a project's own cron jobs
* Fixed a real, previously-unaddressed gap: `ColdBoxAppGenerator`'s generated `aiAgent()` call never passed a `checkpointer:` argument at all, which silently broke human-in-the-loop approval flows through any gateway other than `cli` (bx-ai's `HumanInTheLoopMiddleware.onAttach()` requires one). Every generated agent now always receives one, via a new optional `checkpointer: { type: "cache"|"file"|"jdbc", ...config }` block on `Agent.bx` (defaults to `{ type: "cache" }` if omitted)
* Every push-style gateway now logs to its own `gateway-<type>` file (e.g. `gateway-telegram`) via BoxLang's `writeLog()`, instead of one shared/default app log
* **Added the second push-style chat-platform gateway: Slack**, via Socket Mode (a persistent websocket - no public webhook endpoint needed or generated). A `gateways/*` entry with `type: "slack"` (`botTokenEnvVar` for `chat.postMessage`/`chat.update`, `appTokenEnvVar` for `apps.connections.open`, both required) registers a `SlackGateway`: outbound chunking at Slack's ~3900-char practical block limit, live token-by-token streaming via a placeholder message + `chat.update`, and Block Kit buttons for human-in-the-loop approval. Reconnects are driven reactively by Slack's own protocol signals (a `disconnect` frame or an unexpected socket close), opening a new connection before closing the old one per Slack's documented recommendation, with a 30s scheduler watchdog as a safety net. See `docs/conventions/gateways.md`'s new "Slack's persistent connection" subsection
* `SlackGateway`'s websocket bridges to `java.net.http.WebSocket.Listener` via a small listener class (`models/gateways/support/SlackSocketListener.bx`) that `implements="java:java.net.http.WebSocket$Listener"` directly - BoxLang compiles it as a genuine JVM implementer of the interface, confirmed by handing an instance straight to `HttpClient.newWebSocketBuilder().buildAsync(...)` with no casting error. Only the methods the class actually declares (`onOpen`/`onText`/`onClose`/`onError`) override the JDK interface's `default` methods; the rest (`onBinary`/`onPing`/`onPong`) fall through to the JDK's own defaults automatically (auto pong-reply, auto `request(1)` flow-control). This is the reference pattern any future persistent-connection gateway (Discord) follows
* `ScheduledGatewayBase` gained a shared `onError()`/`dispatchError()` pair (mirroring the existing `onMessage()`/`dispatchInbound()`), so any push-style gateway can report connection-level failures (a reconnect attempt that failed, a socket error) through the same callback-registration shape bx-ai's `IGateway` already uses for inbound messages
* Fixed a real bug in `ColdBoxAppGenerator`'s new `checkpointer:` line (introduced alongside Telegram, above): it rendered `aiMemory( "cache", config: {} )`, mixing a positional argument with a named one, which BoxLang rejects outright - every generated project with a push-style gateway failed to compile. Now renders `aiMemory( memory: "cache", config: {} )`, all-named, matching `aiMemory()`'s real signature (its first parameter is `memory`, not `type`)
* Cleaned up a stray `javacast( "null", "" )` in `TelegramGateway.bx`'s callback-query handling, left over from an earlier draft - this project's convention is always a plain `null`
* **Added the third push-style chat-platform gateway: Discord**, via its real Gateway API (a persistent websocket) rather than the alternative HTTP Interactions Endpoint webhook mode - no Ed25519 signature verification is needed as a result, since interactions arrive over the same authenticated connection. A `gateways/*` entry with `type: "discord"` (`botTokenEnvVar` required; an optional `intents` numeric override, defaulting to `GUILDS`+`GUILD_MESSAGES`+`DIRECT_MESSAGES`+`MESSAGE_CONTENT` = `37377`) registers a `DiscordGateway`: outbound chunking at Discord's 2000-char message limit, live streaming via a placeholder message + a `PATCH` edit, and message-component buttons for human-in-the-loop approval. See `docs/conventions/gateways.md`'s new "Discord's persistent connection" subsection
* Unlike Slack's Socket Mode, Discord's Gateway protocol requires **client-driven heartbeats**: the server's `Hello` frame specifies an interval, and the client must keep sending `Heartbeat` frames on that cadence or the connection is dropped as "zombied". `DiscordGateway` registers this as its own scheduler task, re-registered on every fresh `Hello` since the interval is only known once connected; each tick checks whether the previous heartbeat was ever ACKed before sending the next, reconnecting proactively if not. Reconnects otherwise follow Discord's own documented session model (`Resume` when a session exists and the close code allows it, a fresh `Identify` when it doesn't) and treat a small set of Discord-documented non-recoverable close codes (bad token, bad shard/API-version/intents) as fatal rather than retrying forever
* `DiscordSocketListener.bx` follows the same `implements="java:java.net.http.WebSocket$Listener"` pattern `SlackSocketListener.bx` established - confirming that pattern generalizes cleanly to a second, differently-shaped persistent-connection gateway
* **Added the fourth push-style chat-platform gateway: Email**, and its own new kind of dependency - real, server-level BoxLang/ColdBox module installs. `bx-mail` (adds BoxLang's `bx:mail` component and SMTP sending, configured via `boxlang.json`'s `modules.mail.settings.mailServers`) and `cbmailservices` (ColdBox's own OO/fluent mail-sending abstraction, `MailService@cbmailservices`) are now real `box.json` `dependencies` of this project, so installing `bx-agents` pulls both onto the server too - `cbmailservices` is configured to use its `BXMail` protocol (which itself just calls `bx-mail`'s `bx:mail`), via a new `moduleSettings.cbmailservices` block `ColdBoxAppGenerator` now generates whenever a project has an `email`-type gateway
* A `gateways/*` entry with `type: "email"` (`imapHostEnvVar`/`imapUsernameEnvVar`/`imapPasswordEnvVar`/`fromAddressEnvVar` all required; optional `imapPort` defaulting to 993, `pollIntervalSeconds` defaulting to 60) registers an `EmailGateway`: inbound is a scheduled IMAP poll (hand-rolled via the JDK-standard `jakarta.mail` API - neither `bx-mail` nor `cbmailservices` receive mail, only send it), outbound goes through `MailService@cbmailservices`'s fluent `newMail(...).send()`, resolved manually off `application.cbController.getWireBox()` the same way `ScheduledGatewayBase` already resolves the scheduler (this class is built directly by `aiGateway()`, entirely outside WireBox, so `inject=""` is never honored on it)
* Email's threading and human-in-the-loop are both honestly documented as **degraded** relative to the chat-platform gateways (`getDeclaredCapabilities()` omits `"interactiveActions"`): threading uses real `Message-ID`/`In-Reply-To`/`References` headers for ordinary replies, but HITL has no button/component surface at all - `requestHumanInteraction()` sends a plain-text email listing the allowed decision keywords and correlates the eventual reply via a `[bxagents:<requestID>]` subject-line tag (not `In-Reply-To`, since the outbound approval email's own `Message-ID` isn't exposed by `cbmailservices`' `send()`) - the same technique real email-based support-ticket systems use for the identical reason. See `docs/conventions/gateways.md`'s new "Email - server-level dependencies, and degraded threading/HITL" subsection, and `docs/known-limitations.md` for exactly what was and wasn't verified against real `jakarta.mail`/`cbmailservices` infrastructure this session
* **Fixed a real bug that shipped broken across all four push-style gateways**: the generated `interceptors/GatewaySessionBootstrap.bx` looked gateways up in `aiGatewayRegistry()` by their discovered `gateways/*` entry filename (e.g. `"telegramChannel"`), but bx-ai's real `GatewayRegistry.register()` always keys by the gateway class's own fixed `getName()` (e.g. `"telegram"`) - meaning `GatewaySession` construction threw at ColdBox boot for every project with a push-style gateway. `GatewayGenerator` now emits the correct type-based key (deduplicated - two entries of the same type share one registry slot, a real v1 ceiling this fix also surfaced and documented in `known-limitations.md`), and `GatewayGeneratorSpec.bx` gained a permanent regression test that proves the emitted key resolves a REAL, live-registered gateway instance, not just string content
* **Added the fifth push-style gateway: WhatsApp Business Cloud API**, and its first genuinely webhook-driven (not connection-driven) shape - `WhatsAppCloudGateway` extends bx-ai's `BaseGateway` directly rather than `ScheduledGatewayBase`, since Meta calls us over a public webhook instead of this gateway holding its own outbound connection. Ported directly from [Hermes Agent's](https://github.com/NousResearch/hermes-agent) own real, production WhatsApp Cloud adapter (MIT licensed, read directly this session) - the verify handshake, `X-Hub-Signature-256` HMAC scheme, webhook payload walk, wamid dedup, outbound text/interactive-button-or-list shapes, and every length limit (4096-char messages, 20-char button labels, 1024-char interactive body text) all mirror that implementation, not a from-scratch design
* A `gateways/*` entry with `type: "whatsapp-cloud"` (`accessTokenEnvVar`/`phoneNumberIdEnvVar`/`appSecretEnvVar`/`verifyTokenEnvVar` all required; optional `apiVersion` defaulting to `"v21.0"`) now also generates `handlers/WhatsAppCloud.bx` plus `GET`/`POST /webhooks/whatsapp-cloud` routes - a new generated-route pattern distinct from the existing `http`-type's 3 fixed routes, since Meta's signature scheme (a different HMAC header/format) isn't a reuse of bx-ai's own `HttpGateway`/`GatewaySecurity`
* HMAC-SHA256 signature verification uses `javax.crypto.Mac`/`SecretKeySpec` plus `java.security.MessageDigest.isEqual()` for constant-time comparison - cross-checked independently against both `openssl dgst -hmac` and Python's own `hmac` module before trusting the BoxLang computation in generated code
* **WhatsApp Personal (the unofficial personal-account bridge, originally planned as the sixth push-style gateway) was researched and deliberately descoped, not shipped in any form** - no gateway class, no stub, no `whatsapp-personal` type in the validator or generator. The plan called for porting Hermes Agent's own Node.js/Baileys subprocess-bridge approach, but that was set aside on direct instruction to prefer a native BoxLang/JVM integration over a subprocess bridge. The real published Maven Central artifact for the one MIT-licensed native-Java candidate (`com.github.auties00:cobalt:0.0.10`, formerly WhatsappWeb4j - not its in-progress `master` branch rewrite, which turned out to need Java 25 against BoxLang's Java 21+ baseline) pulls in `com.aspose:aspose-words`, a commercial/proprietary dependency, as a hard compile-time dependency - contaminating the exact license constraint Cobalt was chosen to satisfy. See `docs/known-limitations.md` for the full investigation and what would need to change to revisit this
* **Added the sixth push-style gateway: Microsoft Teams**, webhook-driven like WhatsApp Cloud (`TeamsGateway` extends `BaseGateway` directly - no scheduler task or connection to manage). Ported from [Vercel Eve's](https://github.com/vercel/eve) real Teams channel (`packages/eve/src/public/channels/teams/`, MIT licensed) - the OAuth2 client-credentials outbound token flow, the inbound bearer-JWT verification against Bot Connector's own JWKS, the `v3/conversations/{id}/activities[/{activityId}]` REST triad, and the Adaptive Card human-in-the-loop shape (one `Action.Submit` button per allowed decision) all mirror that implementation. Hermes Agent's own `msgraph_webhook.py` was investigated and found to be an unrelated Microsoft product surface (Graph change-notification webhooks, not Bot Framework messaging, with no working outbound send) - nothing from it was ported
* A `gateways/*` entry with `type: "teams"` (`appIdEnvVar`/`appPasswordEnvVar` required; optional `tenantId`, defaulting to `"botframework.com"` for multi-tenant apps) generates `handlers/Teams.bx` plus a single `POST /webhooks/teams` route - one route, not two, since Bot Framework has no GET verify-handshake equivalent to Meta's `hub.challenge`
* RS256 JWT verification (JWKS fetch, `java.security.KeyFactory`/`RSAPublicKeySpec`/`BigInteger` JWK-to-PublicKey construction, `java.security.Signature` signature check, `aud`/`iss`/`exp`/`nbf` claim validation) is built entirely from BoxLang's own Java interop - no external JWT library dependency. Verified empirically against a real, locally-generated RSA keypair and hand-signed test JWTs (valid → accepted; tampered signature, wrong audience, wrong issuer, and expired all independently → rejected with 401), both in a standalone smoke test and as `TeamsGatewaySpec.bx`'s own permanent test coverage
* v1 scope is personal (1:1 DM) Teams conversations only - group/channel messages (which need bot-mention gating and a different reply-threading model) are out of scope, matching every other push-style gateway's DM-first v1 scoping
* **Added the seventh push-style gateway: Twilio SMS**, webhook-driven like WhatsApp Cloud/Teams. Ported from [Vercel Eve's](https://github.com/vercel/eve) real Twilio channel (`packages/eve/src/public/channels/twilio/`, MIT licensed) - the form-urlencoded inbound body, the `X-Twilio-Signature` HMAC-SHA1/base64 verification scheme (a genuinely different construction than every other webhook gateway's HMAC-SHA256/hex - the exact request URL plus every sorted `key & value` pair, no separators), the dual-path response model (a synchronous empty TwiML `<Response></Response>` ack, with the real reply sent later via a separate async Messages API call), and the outbound `Messages.json` Basic-Auth REST call all mirror that implementation
* A `gateways/*` entry with `type: "twilio"` (`accountSidEnvVar`/`authTokenEnvVar`/`fromEnvVar` required; optional `messagingServiceSid` and `publicUrl` overrides) generates `handlers/Twilio.bx` plus a single `POST /webhooks/twilio` route
* v1 is SMS-text only - Eve's own Twilio channel is a combined SMS+voice channel; every voice-specific piece (`/voice` routes, `<Gather>`/`<Say>` TwiML, call transcription) was deliberately left out. Unlike Eve (which has no length-limiting logic of its own - confirmed absent by grepping its source), `TwilioGateway` still chunks outbound text at 1600 chars (Twilio's own documented single-message ceiling) for consistency with every other gateway here
* Human-in-the-loop is degraded the same way Email's is (no native button/card affordance in SMS) - `requestHumanInteraction()` sends a plain-text SMS listing allowed decisions, correlated back to the pending request by the sender's own phone number (conversationID) rather than a subject-line tag, since SMS has no subject line the way email does
* The HMAC-SHA1/base64 signature algorithm was cross-verified this session against an independently computed Python `hmac`/`hashlib` reference value before trusting the BoxLang implementation, the same discipline already used for WhatsApp Cloud's HMAC-SHA256 scheme
* **Added the eighth push-style gateway: GitHub**, an agent that responds to `@mentions` in issue/PR comments, treating each issue/PR (or inline review-comment thread) as a chat conversation. Ported from [Vercel Eve's](https://github.com/vercel/eve) real GitHub channel (`packages/eve/src/public/channels/github/`, MIT licensed) - `X-Hub-Signature-256` verification is confirmed the identical construction to WhatsApp Cloud's own Meta scheme (the only webhook gateway here that reuses another one's exact signature algorithm), the `@mention`-gated dispatch, the issue-vs-review-thread conversation model, and the outbound Issues/PR-review-comment REST endpoints all mirror that implementation. Only `issue_comment`/`pull_request_review_comment` events with `action: "created"` dispatch, matching Eve's own only-default-handled event kinds
* A `gateways/*` entry with `type: "github"` (`tokenEnvVar`/`webhookSecretEnvVar`/`botNameEnvVar` required; optional `apiBaseUrl` override) generates `handlers/GitHub.bx` plus a single `POST /webhooks/github` route. v1 auth is a plain personal access token, not Eve's own GitHub App JWT + installation-token flow - simpler and more directly portable for a first cut; no repo checkout/code-editing (Eve's own `checkout.ts`) was ported either - this is a comment-in/comment-out chat surface only
* Bot-loop prevention mirrors Eve's own three-part guard (`type: "Bot"` authors, a `{botName}[bot]` login, or this gateway's own `<!-- bxagents:posted -->` marker are all ignored). Unlike Eve (which has no delivery-id dedup at all), `GitHubGateway` dedups by `X-GitHub-Delivery` via a bounded FIFO cache, matching WhatsApp Cloud's own `wamid` dedup. Human-in-the-loop is degraded the same way Twilio's is - `requestHumanInteraction()` asks the human to `@mention` the bot again in a reply, correlated by conversationID
* **A real bug caught by testing, not just reading**: the mention-extraction helper's substring logic called `left( body, 0 )` whenever a comment's `@mention` occurred at the very start (a very common case) - BoxLang's `left()` throws `"Count cannot be zero"` rather than returning `""` for a zero count. Caught via a standalone real-BoxLang smoke test before it ever reached the permanent test suite, fixed by explicitly branching around the zero-length case
* **Added the ninth push-style gateway: Signal**, and a genuinely new transport shape in this codebase - Server-Sent Events. `SignalGateway` extends `ScheduledGatewayBase` (like Telegram/Slack/Discord/Email), but instead of a poll task or a websocket, it holds a single long-lived SSE connection open via `java.net.http.HttpClient`'s async API (`sendAsync()` + `BodyHandlers.ofLines()`), reading one JSON event per line pushed down the same response body, and sends outbound messages as plain JSON-RPC 2.0 calls against the same daemon. Ported from [Hermes Agent's](https://github.com/NousResearch/hermes-agent) own real Signal channel - the SSE/JSON-RPC wire shapes, the exponential reconnect-backoff constants (2s to 60s, +20% jitter), and the 30s/120s idle watchdog are all read directly from that source
* Signal has no official bot API - `SignalGateway` talks entirely to an external [`signal-cli`](https://github.com/AsamK/signal-cli) daemon (`signal-cli -a <account> daemon --http=...`), a real, manually-managed prerequisite outside this project's control, the same relationship `EmailGateway` has with an external IMAP/SMTP server. A `gateways/*` entry with `type: "signal"` (`accountEnvVar` required; optional `httpUrl` override, defaulting to `http://127.0.0.1:8080`) registers it - no generated route or handler, since it's a connection-holding gateway like Telegram/Slack/Discord/Email, not a webhook one
* v1 is DM-only (Signal group conversations are out of scope, matching Hermes's own opt-in/off-by-default handling). Human-in-the-loop is degraded the same way Twilio/GitHub's fallback is - Signal reactions/read-receipts are write-only cosmetic status in signal-cli's own API, not a real answer channel, so `requestHumanInteraction()` falls back to a plain-text message listing the allowed decisions, correlated by conversationID
* Two BoxLang landmines were found and resolved while building this gateway, both self-inflicted in throwaway test scripts rather than bugs in `SignalGateway.bx` itself: a local variable named `request` silently collides with BoxLang's own reserved `request` scope instead of behaving as a plain variable (the same class of bug this project's own `GatewaySessionBootstrap.bx` generator code independently found for `session` earlier); and a `try/catch` placed directly at the top level of a standalone `.bxs` script (not inside a function) can trigger a `java.lang.VerifyError: Inconsistent stackmap frames` - a real bytecode-verification limitation of BoxLang's top-level-script compiler, not of the code under test. Both are documented in `docs/known-limitations.md` as general cautions for future BoxLang code in this project
* **Added the v1 web chat UI**, a third `gateways/*` exposure kind alongside `exposes: "agent"`/`"mcp"` - `exposes: "webui"` generates a small, dependency-free, single-page chat UI (vanilla HTML/CSS/JS, no Bootstrap/AlpineJS/Vite build step) served as a real static file at `<path>/index.html`, plus its own dedicated `route( "<path>/api" ).toAi( "GeneratedAgent" )`. Ships **pre-built and vendored inside BX Agents itself** - `bxAgents build` never runs `npm install`/`npm run build`, and a generated project never needs Node/npm installed at all, a deliberate "small first, then we grow" v1 scope decision
* The page talks to its generated API over `POST <path>/api/stream` via `fetch()` + a manual `ReadableStream` reader - `EventSource` can't do `POST` or set custom headers, both needed here. **The wire format is the full bx-ai chunk envelope, not a token wrapper**: ColdBox's `toAi()` stream sub-route does `emitter.send( chunk, "chunk" )`, forwarding each chunk verbatim, so the page reads `choices[0].delta.*`. ColdBox's published AI Routing docs show a `data: {"token":"..."}` shape that its own source never produces - an earlier revision of this page believed those docs and consequently rendered nothing at all against a live agent
* **The UI now surfaces reasoning and tool calls**, which were already arriving on that same envelope and being thrown away: `delta.reasoning` (normalized across every provider by bx-ai) renders as a collapsed "Thinking" strip, and `delta.tool_calls` as collapsed per-call chips. Tool-call arguments stream as partial JSON fragments keyed by `index`, so they're accumulated per index rather than assuming any one chunk carries a complete call. Both default on; `showReasoning`/`showToolCalls` turn them off per entry. A human-in-the-loop suspension (a `middleware_stop` sentinel chunk) surfaces a notice instead of silently rendering nothing
* **Fixed a shared-conversation bug by scoping the agent's IDENTITY, not its memory type.** Every memory an agent holds is keyed by `(userId, conversationId)` - and an agent can hold several at once (`AiAgent`'s `memories` is an array, iterated with the same pair). `run()`/`stream()` fall back to `""` for both when nothing supplies them, so **every visitor to a browser-facing app landed in one shared bucket**, whatever memories were configured. Two things were missing: the generated `Application.bx` hardcoded `this.sessionManagement = false`/`setClientCookies = false`, so there was no session id to scope by; and the web UI's API was a `toAi()` route, whose actions forward `body.options` to the runnable verbatim - meaning a `userId` could only ever be one the *caller* sent, which is a request rather than an identity
* A `webui` project now turns session management on (cookies plus a 60-minute timeout) and gets its own generated **`handlers/ChatUi.bx`**, which passes `session.sessionId` as the agent's `userId` on **all three runner shapes - `invoke`, `stream` and `batch`**. It keeps `toAi()`'s exact route shape (`/invoke`, `/stream`, `/batch`, `/info`) and its exact SSE wire format, so the shipped page needed no changes; it differs only in reading the user id from the server. `exposes: "agent"` still uses `toAi()` unchanged
* Because the identity is server-issued, **no memory type is forced** - a project stays free to configure whichever memories it wants, one or many, without any of them collapsing into a shared bucket. Added a `memory` key to `Agent.bx` (same shape as `checkpointer`), threaded through the whole agent tree so subagents inherit it and any node can override
* The UI still sends a `conversationId`, now purely to distinguish several conversations belonging to the *same* visitor (it's what the **New** button rotates) rather than as the isolation boundary
* **Assistant replies now render markdown** - fenced/inline code, bold/italic, links, lists, headings - applied **escape-first**, so the model's text is HTML-escaped before any tag is introduced and no model output can become live markup. Link hrefs are allowlisted to `http(s)`/`mailto`, so a `javascript:` URL is never turned into an anchor. Verified in a real browser against script/img-onerror/iframe/svg-onload/`javascript:` payloads: zero live nodes, nothing executed
* **Composer and transcript reworked**: a `textarea` (Enter sends, Shift+Enter newlines, auto-grows to ~6 lines) replaces the single-line input; a **Stop** button aborts an in-flight turn via `AbortController` and *keeps* what already streamed; auto-scroll only follows when you're already at the bottom, so reading back mid-stream no longer yanks you down; assistant replies get a **Copy** button that yields the original markdown rather than the rendered text; and the transcript is an `aria-live="polite"` log with a labelled input
* **Added branding and theming config** to the `webui` entry: `title`, `subtitle`, `icon` (an emoji rendered into an inline-SVG favicon *and* the header, or an image URL), `welcome`, `placeholder`, `footer`. A `theme` block maps onto the page's 23 CSS custom properties (`accent`, `radius`, `font`, `bubble*`, `reasoning*`, `tool*`, …) with a nested `theme.dark` for dark-mode overrides; an unknown token **fails the build** rather than being silently ignored, so a typo doesn't leave you wondering why your brand color never applied. Hex colors are written **bare** (`"0f766e"`) and the generator adds the leading hash back - BoxLang starts interpolation at `#` in both quote styles, so the literal form is a parse error unless doubled. Anything the tokens don't cover goes in `resources/webui/theme.css` (overridable via `themeFile`), inlined last so it wins - and being real CSS, ordinary hex works there normally
* An optional `apiKeyEnvVar` on the `webui` entry is a simple, toggleable gate, not a full login system - when set, a generated `interceptors/WebUiAuthGate.bx` (a `preProcess` interceptor) requires a matching `X-API-Key` header on every request under `<path>/api/*`, compared via `java.security.MessageDigest.isEqual()` (the same constant-time-compare discipline every webhook gateway's own signature check already uses). The static shell itself (`<path>/index.html`) is deliberately never gated - only `<path>/api/*` is - since a browser's plain page navigation can't send a custom header, and the shell is exactly what prompts for the key in the first place
* The vendored `webui/index.html` template lives as a real, separate file next to the new `WebUiGenerator.bx` (not a BoxLang string literal) - confirmed empirically this session that embedding raw CSS (`#fff`-style hex colors) directly in BoxLang string literals fails to parse, since `#` always starts interpolation in both single- and double-quoted BoxLang strings. Resolved via `getCurrentTemplatePath()` (confirmed to resolve to the generator's own file location, not the caller's, regardless of dev-mapped vs. genuinely-installed-module context) rather than any hardcoded mapping prefix. `build.gradle`'s `createModuleStructure` task now also copies `**/*.html` alongside `.bx`/`.bxm`/`.bxs`, so the template ships in the real packaged module too
* Added `examples/webui-agent/` (with the gate turned on, to demonstrate the full flow) to the examples catalog
